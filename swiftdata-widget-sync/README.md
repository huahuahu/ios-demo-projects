# SwiftDataResearch

This demo researches bidirectional data sharing between an iOS app and a WidgetKit extension using SwiftData.

## Blog Topic

Use this project while researching whether an app and its widget can read and write the same SwiftData store through an App Group container.

The app can insert, update, and delete notes. The widget reads the same store and has interactive buttons backed by `AppIntent` to insert or update notes from the widget process.

## Requirements

- Xcode with iOS 26 SDK
- XcodeGen 2.45 or newer
- Swift 6.0

## Generate and Open

```bash
cd swiftdata-research
xcodegen generate
open SwiftDataResearch.xcodeproj
```

## Run and Test

```bash
cd swiftdata-research
xcodebuild test \
  -project SwiftDataResearch.xcodeproj \
  -scheme SwiftDataResearch \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro Max,OS=latest'
```

## Logging

The demo uses `os.Logger` with subsystem `com.huahuahu.demo.SwiftDataResearch`. Useful categories are:

- `SharedStore`: SwiftData container creation, fetches, saves, and widget reload requests.
- `App`: app button actions, visible-list refreshes, and `NSPersistentStoreRemoteChange` notifications.
- `History`: SwiftData transaction-history token loading, transaction fetches, summaries, and cleanup.
- `Widget`: widget timeline reads and interactive `AppIntent` writes.

Filter these logs in Xcode's console or Console.app by subsystem/category while testing App and Widget writes.

## Key Files

- `SharedNotes/ResearchNote.swift`: the SwiftData `@Model` type shared by app, widget, and tests.
- `SharedNotes/OperationLog.swift`: records business-level user operations alongside SwiftData transaction history.
- `SharedNotes/SharedStore.swift`: creates the App Group SwiftData container and exposes write helpers for notes and operation logs.
- `SwiftDataResearch/ContentView.swift`: the app-side probe that listens for store-change notifications, consumes transaction history, and refreshes the visible list.
- `SwiftDataResearchWidget/SwiftDataResearchWidget.swift`: the widget timeline reader and interactive widget UI.
- `SwiftDataResearchWidget/WidgetNoteIntents.swift`: widget-side writes through `AppIntent`.
- `SwiftDataResearchTests/SwiftDataResearchTests.swift`: in-memory SwiftData round-trip test.

## Research Notes

- The shared store path is `group.com.huahuahu.demo.SwiftDataResearch/SwiftDataResearch.store`.
- App writes call `WidgetCenter.shared.reloadTimelines(ofKind:)` so the widget can reread the shared store.
- The app uses `SharedStoreHistoryMonitor` to listen for `NSPersistentStoreRemoteChange`, fetch `DefaultHistoryTransaction` records since the last stored token, and reload widget timelines when shared `ResearchNote` history changes.
- Widget writes happen in an `AppIntent`; the app listens for `NSPersistentStoreRemoteChange`, consumes SwiftData transaction history, then refreshes its list. App foreground activation still triggers a fallback fetch.
- App and Widget writes set `ModelContext.author` before saving, so transaction history can distinguish authors such as `App` and `Widget`.
- New notes include a millisecond timestamp in both the title and detail, making App and Widget inserts easy to distinguish while testing.
- Transaction logs include `transactionIdentifier`, `storeIdentifier`, `author`, `bundleIdentifier`, `processIdentifier`, and `timestamp`. `transactionIdentifier` is generated by SwiftData for each store transaction. `storeIdentifier` identifies the SwiftData backing store that produced the transaction. These are history metadata values and are not intended to be manually assigned per write; use `ModelContext.author`, `OperationLog`, or model fields for caller-controlled labels.
- Each write also inserts an `OperationLog`, which records business intent such as `insertNote`, `updateLatestNote`, `deleteSelectedNotes`, or `deleteAllNotes`. Transaction history explains what changed in the store; operation logs explain why the app/widget made that change.
- App-side action buttons use an explicit bordered `ButtonStyle`. In a `List` row, multiple default SwiftUI buttons can be promoted into row-level actions, which may make one tap invoke more than the tapped button.
- A paid Apple Developer team and matching App Group capability may be required to run this on a real device or signed simulator build.
- This demo intentionally keeps the SwiftData model source shared between targets. If SwiftData schema identity changes across modules in practice, the next step is moving the shared model into a separate framework or Swift package module used by both targets.
